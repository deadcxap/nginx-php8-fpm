# nginx + PHP-FPM + Node.js

Образ собирается независимо в этом форке и публикуется в
`ghcr.io/deadcxap/nginx-php8-fpm`. В него входят nginx, PHP-FPM, Composer,
распространённые расширения PHP и, по умолчанию, Node.js/npm. Варианты для
`linux/amd64` и `linux/arm64` собираются и проверяются на нативных раннерах GitHub.

Оригинальный проект — [tangramor/nginx-php8-fpm](https://github.com/tangramor/nginx-php8-fpm).
Лицензия BSD-3-Clause и указание авторства сохранены. Готовый образ автора
оригинального проекта больше не используется при сборке.

## Быстрый старт с Docker Compose

В репозитории есть два самостоятельных примера:

- [compose.yaml](compose.yaml) — nginx + PHP-FPM + Composer + Node.js/npm.
- [compose.without-node.yaml](compose.without-node.yaml) — тот же набор без Node.js/npm.

Нужны Docker Engine и плагин Docker Compose (`docker compose`). Поместите своё
PHP-приложение в каталог `app/` рядом с Compose-файлами: он монтируется в
`/var/www/html`. Для Laravel и других приложений с каталогом `public/` измените
`WEBROOT` в выбранном файле на `/var/www/html/public`.

Из корня репозитория запустите один из примеров:

```sh
# С Node.js/npm:
docker compose up -d

# Или без Node.js/npm:
docker compose -f compose.without-node.yaml up -d
```

Откройте [http://localhost:8080](http://localhost:8080). При первом запуске
Compose скачает образ. Если образ в GHCR ещё не опубликован или для доступа
нужна авторизация, см. [первую публикацию](#github-actions-и-первая-публикация).

Порт хоста (`8080`), часовой пояс и идентификаторы рабочих процессов задаются
непосредственно в Compose-файле. В примерах используются `PUID=1000`,
`PGID=1000`, `UMASK=022`. В Linux укажите значения `id -u` и `id -g` владельца
приложения, а в Unraid — `PUID=99`, `PGID=100`. Оставьте запуск контейнера от
root по умолчанию: это нужно, чтобы образ применил указанные идентификаторы
до запуска рабочих процессов. Зависимости приложения устанавливайте по
инструкции своего проекта.

В обоих файлах **в комментариях** приведён необязательный пример с MariaDB.
Чтобы его включить, раскомментируйте сервис `db`, том `db-data` и настройки
`DB_*` приложения, затем замените пароли из примера. Приложение подключается
к `db:3306`; данные MariaDB хранятся в именованном томе и сохраняются между
вызовами `down` и `up`.

```sh
docker compose logs -f app
docker compose down

# Обновить образ и пересоздать контейнер:
docker compose pull
docker compose up -d
```

Для варианта без Node.js добавляйте `-f compose.without-node.yaml` к каждой
команде `docker compose`. Дополнительные переменные окружения и требования
к правам на запись описаны в разделе [настройки контейнера](#настройка-контейнера).

## Политика обновлений

| Компонент | Источник по умолчанию |
| --- | --- |
| PHP | Официальный `php:fpm-alpine`: последняя стабильная версия PHP и используемый по умолчанию выпуск Alpine |
| Node.js | Официальный `node:lts-alpine<release>`: последняя LTS-версия на том же выпуске Alpine, что и PHP |
| npm | Последняя стабильная версия `npm@latest` с обновлёнными зависимостями в пределах заявленных диапазонов версий |
| nginx и динамические модули | Последние пакеты из официального репозитория nginx mainline |
| Composer | Официальный `composer:latest` |
| Расширения PHP | Расширения из состава PHP и стабильные релизы PECL |
| Системные пакеты | Последние доступные пакеты из выбранных стабильных репозиториев Alpine |

Версии компонентов среды выполнения в сборке не зафиксированы. Скрипт
`build.sh` скачивает актуальный образ PHP, определяет его digest для текущей
сборки, считывает версию Alpine и подбирает соответствующий вариант Node.js.
Digest определяется заново при каждом запуске, а не закрепляется навсегда.
Сборки используют `--pull --no-cache` и `apk upgrade --no-cache`, чтобы обновлять
как базовые образы, так и установленные пакеты.

Расширения PHP устанавливаются с помощью
[mlocati/docker-php-extension-installer](https://github.com/mlocati/docker-php-extension-installer)
из последнего образа установщика. Он управляет нативными зависимостями
расширений и удаляет временные инструменты сборки. Для Imagick используется
стабильный релиз без прежнего локального патча исходников. Composer копируется
из официального образа вместо скачивания установщика по HTTP. npm и входящие
в него зависимости обновляются отдельно: даже последний релиз npm может
содержать устаревшие зависимости. Обновление соблюдает заявленные npm диапазоны
версий и требования совместимости с Node.js, не устанавливая принудительно
несовместимые версии. Дополнительные зеркала по умолчанию отключены.

Плавающие каналы обновлений могут приносить и новые мажорные версии. Новый
релиз PHP может временно оказаться несовместимым с расширением, а нужные
пакеты Node.js или nginx для соответствующего выпуска Alpine могут ещё
отсутствовать. В таком случае сборка завершается ошибкой, а опубликованные
теги остаются на последнем успешном релизе. Автоматического перехода на старую
версию или предварительный релиз нет. Следите за неудачными запусками Actions:
`latest` означает последнюю **успешную** сборку, а не гарантию устранения всех
известных уязвимостей.

## Теги образов

| Тег | Содержимое |
| --- | --- |
| `latest` | nginx + PHP-FPM + Composer + Node.js/npm |
| `latest-without-node` | nginx + PHP-FPM + Composer |
| `nginx<version>_php<version>_node<version>` | Образ с указанными версиями nginx, PHP и Node.js |
| `nginx<version>_php<version>` | Образ с указанными версиями nginx и PHP, без Node.js |

Теги формируются из фактически установленных версий, включая patch-версии,
например `nginx1.28.0_php8.5.2_node25.6.0` или `nginx1.28.0_php8.5.2`. Это примеры
формата: доступные теги зависят от успешных сборок. Перед публикацией версии
для amd64 и arm64 должны совпасть в пределах каждого варианта образа.

Теги с версиями и `latest` / `latest-without-node` содержат манифесты для
amd64/arm64. У образов для отдельных архитектур к тегу с версиями добавляется
суффикс `-amd64` или `-arm64`. Повторная сборка с теми же версиями nginx/PHP/Node.js
обновляет существующий тег: расширения, npm или системные пакеты могли
измениться. Для фиксации конкретного образа и гарантированного отката используйте
digest. Прежние теги `without-node` и `build-*` больше не публикуются и не
обновляются; существующие теги в реестре автоматически не удаляются.

После первой успешной публикации:

```sh
docker pull ghcr.io/deadcxap/nginx-php8-fpm:latest
docker run --rm -p 8080:80 \
  -v "$PWD:/var/www/html" \
  -e WEBROOT=/var/www/html/public \
  ghcr.io/deadcxap/nginx-php8-fpm:latest
```

В репозитории нет приложения и TLS-сертификатов. Подключите своё приложение
в `/var/www/html`; для порта 443 предоставьте собственную конфигурацию TLS
для nginx. Публикация нового образа не обновляет уже запущенный контейнер:
скачайте новый образ и пересоздайте контейнер в своём окружении.

## GitHub Actions и первая публикация

Workflow из `.github/workflows/images.yml` запускается:

- при push в `master`;
- для pull request — только проверки, без разрешения на публикацию пакетов;
- каждый понедельник в **03:17 UTC** (06:17 по Москве);
- вручную через **Actions → Build, test and publish images → Run workflow**;
- по аутентифицированному событию `repository_dispatch` типа `rebuild`.

Для каждого варианта и архитектуры образ собирается один раз. Затем workflow
записывает установленные версии, проверяет образ, сохраняет этот же образ
и его тег с версиями в артефакты и сканирует образ с помощью Trivy. Проверка
блокирует публикацию при наличии **уязвимостей HIGH/CRITICAL, для которых доступны исправления**. Полный
JSON-отчёт также содержит уязвимости меньшей серьёзности и проблемы без
исправлений. Ошибки сканера или его базы данных завершают задание с ошибкой,
а не позволяют обойти проверку. Отчёты хранятся в артефактах Actions 30 дней.

Только после успешного прохождения всех четырёх сборок отдельное задание
публикации загружает сохранённые архивы и отправляет их в GHCR без повторной
сборки. Задание проверяет теги с версиями, записанные на нативных раннерах,
публикует оба манифеста с версиями, затем обновляет `latest` и
`latest-without-node`. Ошибка сборки, тестов, сканирования или несовпадение
версий не обновляет ни один плавающий тег. Операции с реестром не образуют
транзакцию: сетевая ошибка во время последних двух обновлений тегов может
оставить их на разных сборках.

Чтобы включить публикацию:

1. Закоммитьте файлы и отправьте их в `master` своего форка.
2. Включите GitHub Actions для форка, если GitHub этого требует. Политика
   Actions репозитория должна разрешать действия GitHub/Docker, используемые
   в workflow.
3. Запустите workflow вручную или дождитесь запуска после push. Задание
   публикации использует автоматически выдаваемый `GITHUB_TOKEN` с
   разрешением `packages: write`; аккаунт Docker Hub или отдельный PAT
   для публикации из Actions не нужны.
4. Откройте новый пакет в своём аккаунте GitHub. Если нужно разрешить
   скачивание без авторизации, установите видимость **Public** в настройках
   пакета. Новые пакеты GHCR по умолчанию приватные, даже если репозиторий
   публичный.

Workflow определяет пространство имён GHCR и метку OCI с адресом исходников
по репозиторию, в котором запускается. Для этого форка адрес образа —
`ghcr.io/deadcxap/nginx-php8-fpm`. Если пакет с таким именем уже существует,
перед публикацией предоставьте Actions этого репозитория доступ к нему
в настройках пакета.

GitHub Actions закреплены за конкретными коммитами независимо от плавающих
каналов версий компонентов. Dependabot еженедельно проверяет эти ссылки.
Просматривайте и сливайте его PR с обновлениями, чтобы обновлять инструменты
workflow.

### Автоматические сборки неактивного репозитория

GitHub может отключить запуски по расписанию в публичном репозитории после
60 дней без активности. Сборки по расписанию не являются надёжным исключением
из этого правила. Для работы без постоянного участия используйте внешний
планировщик, отправляющий событие `rebuild`, либо включайте расписание заново,
когда GitHub его отключает.

Например, выполняйте следующую команду в своём планировщике с авторизованным
GitHub CLI и учётной записью, которой разрешена отправка событий в репозиторий:

```sh
gh api --method POST repos/deadcxap/nginx-php8-fpm/dispatches \
  -f event_type=rebuild
```

Workflow должен существовать в ветке по умолчанию. Внешний планировщик и его
учётные данные настраиваются отдельно: репозиторий не создаёт внешних заданий.
Если GitHub отключил workflow целиком, включите его перед отправкой события.
См. [документацию GitHub о расписаниях](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

## Локальная сборка и проверки

Нужны Bash, Docker Engine и Docker Buildx. По умолчанию скрипты собирают образ
для архитектуры локального Docker. Для другой платформы используйте нативные
раннеры или настроенную эмуляцию.

```sh
# Полный образ; каждый запуск обновляет зависимости.
./build.sh

# Тот же Dockerfile, цель without-node.
./build.withoutNodejs.sh

# Выбрать новейший канал Current для Node.js вместо LTS.
NODE_CHANNEL=current IMAGE=nginx-php8-fpm:current ./build.sh

# Использовать локальный тег и выполнить те же проверки, что и в CI.
IMAGE=nginx-php8-fpm:test ./build.sh
./scripts/smoke-test.sh nginx-php8-fpm:test with-node
./scripts/image-info.sh nginx-php8-fpm:test

# Просканировать экспортированный образ; при блокировке публикации код выхода ненулевой.
docker image save -o /tmp/nginx-php8-fpm.tar nginx-php8-fpm:test
./scripts/scan-image.sh /tmp/nginx-php8-fpm.tar ./reports
```

Через переменные окружения можно переопределить `IMAGE`, `TARGET`, `PLATFORM`,
`PHP_IMAGE`, `NODE_CHANNEL`, `NODE_IMAGE`, `APKMIRROR` и метаданные OCI `IMAGE_*`.
Дополнительные аргументы `build.sh` передаются в Buildx. Например, уменьшить
параллелизм компиляции расширений можно аргументом `--build-arg IPE_PROCESSOR_COUNT=2`.

Прямая команда `docker build --pull --no-cache --target with-node .` также
работает, если плавающие теги PHP и Node.js по умолчанию используют одинаковый
выпуск Alpine. Предпочтительнее скрипт: он автоматически подбирает совпадающие
выпуски Alpine. При несовпадении прямая сборка завершится ошибкой, чтобы
не публиковать потенциально несовместимые бинарные файлы.

Прежние `Dockerfile.withoutNodejs` и дублирующий скрипт запуска заменены общей
целью `without-node` и скриптом `start.sh`. Старая команда
`build.withoutNodejs.sh` остаётся доступной как обёртка.

## Настройка контейнера

| Переменная | Значение по умолчанию / поведение |
| --- | --- |
| `WEBROOT` | `/var/www/html`; для Laravel используйте `/var/www/html/public` |
| `TZ` | `UTC`; поддерживает установленные часовые пояса, например `Europe/Moscow` |
| `PUID` | `101`; числовой UID рабочих процессов nginx и PHP-FPM |
| `PGID` | `101`; числовой идентификатор основной группы рабочих процессов nginx и PHP-FPM |
| `UMASK` | `022`; маска прав для скриптов запуска и процессов под управлением Supervisor; `002` или `0002` разрешают группе запись в новые файлы |
| `PHP_MEM_LIMIT` | `128` МиБ; целое число |
| `PHP_POST_MAX_SIZE` | `100` МиБ; целое число |
| `PHP_UPLOAD_MAX_FILESIZE` | `100` МиБ; целое число |
| `ERRORS` | Установите `1`, чтобы показывать ошибки PHP; по умолчанию отключено |
| `HIDE_NGINX_HEADERS` | `1`; установите `0`, чтобы показывать версии nginx/PHP в заголовках |
| `PHP_REDIS_SESSION_HOST` | Необязательное имя хоста или IPv4-адрес Redis для сессий, порт 6379 |
| `COMPOSERMIRROR` | Необязательный URL репозитория Composer |
| `NPMMIRROR` | Необязательный URL реестра npm; нужен вариант образа с Node.js |
| `REAL_IP_HEADER` | Установите `1`, чтобы доверять `X-Forwarded-For` от `REAL_IP_FROM` |
| `REAL_IP_FROM` | Один доверенный адрес, имя хоста или CIDR; по умолчанию `172.16.0.0/12` |
| `CREATE_LARAVEL_STORAGE` | Установите `1`, чтобы создать доступные для записи каталоги Laravel storage и пользователя `sail` |
| `RUN_SCRIPTS` | Установите `1`, чтобы выполнять файлы из `/var/www/html/scripts/` в порядке их имён |
| `ENABLE_XDEBUG` | Устанавливайте `1` только в производном образе с установленным Xdebug; используйте актуальные настройки `XDEBUG_MODE` / `XDEBUG_CONFIG` |

Ошибки PHP/nginx и журнал доступа выводятся в логи контейнера. Запись ошибок
PHP в stderr всегда включена, поэтому `PHP_ERRORS_STDERR` больше не нужна.
Часовой пояс по умолчанию изменён с `Asia/Shanghai` на `UTC`. Зеркала включаются
явно. Node.js/npm входят в полный образ; Yarn не установлен.

При каждом запуске и перезапуске контейнер также выводит в логи установленные
версии Alpine, nginx, PHP и Composer, версии Node.js/npm при их наличии и тег,
сформированный из версий nginx/PHP/Node.js. Отчёт содержит включённые модули
PHP, параметры сборки nginx и установленные пакеты динамических модулей nginx.
Посмотреть его можно командой `docker compose logs app`, а вывести повторно —
через `docker compose exec app runtime-info`. Команда `runtime-info --tag`
выводит только тег с версиями и используется при публикации образов.

При запуске следующие необязательные файлы приложения копируются до применения
настроек из переменных окружения:

| Файл приложения | Путь назначения |
| --- | --- |
| `/var/www/html/conf/nginx.conf` | `/etc/nginx/nginx.conf` |
| `/var/www/html/conf/nginx-site.conf` | `/etc/nginx/conf.d/default.conf` |
| `/var/www/html/conf/nginx-site-ssl.conf` | `/etc/nginx/conf.d/default-ssl.conf` |

Рабочие процессы nginx и PHP-FPM запускаются от пользователя `nginx`,
Supervisor — от root. PHP-FPM слушает сокет `/var/run/php-fpm.sock`. Обеспечьте
рабочему пользователю права на чтение файлов приложения и на запись в
необходимые каталоги. Настройки PHP пересоздаются при запуске, поэтому
перезапуск не накапливает повторяющиеся директивы.

Для Unraid установите `PUID=99`, `PGID=100` и `UMASK=022` в шаблоне контейнера.
Учётная запись `nginx` использует эти числовые идентификаторы, в том числе
если такой GID уже существует в Alpine. UID/GID должны быть десятичными целыми
числами от 1 до 4294967294; значение 0 запрещено. `UMASK` принимает три
восьмеричные цифры с необязательным ведущим нулём. При перезапуске настройки
сохраняются. Оставьте запуск контейнера от root по умолчанию, чтобы он мог
настроить учётные записи до снижения привилегий nginx/PHP-FPM.

Владелец и права подключённых каталогов приложения автоматически не меняются.
Каталоги, требующие записи, должны заранее разрешать её выбранным UID/GID.
Опциональная настройка `CREATE_LARAVEL_STORAGE=1` по-прежнему создаёт каталог
Laravel storage и меняет его владельца. Маска влияет только на вновь создаваемые
файлы: она не меняет права существующих файлов и не предоставляет доступ
к каталогам. Права новых файлов по умолчанию — 0644 при `022` и 0664 при `002`,
если приложение явно не запрашивает более строгие права.

### Переопределение настроек nginx, PHP и Node.js

Настройки контейнера можно менять без пересборки образа. Для
основных параметров используйте переменные окружения из таблицы выше, а для
остальных — подключённые файлы конфигурации. Например, создайте
`compose.override.yaml` рядом с `compose.yaml`:

```yaml
services:
  app:
    environment:
      PHP_MEM_LIMIT: "512"
      PHP_POST_MAX_SIZE: "128"
      PHP_UPLOAD_MAX_FILESIZE: "120"
      NODE_OPTIONS: "--max-old-space-size=1024"
    volumes:
      - ./docker/php.ini:/usr/local/etc/php/conf.d/zzz-custom.ini:ro
      - ./docker/nginx-site.conf:/var/www/html/conf/nginx-site.conf:ro
```

Compose автоматически объединяет этот файл с `compose.yaml`, сохраняя
подключение приложения, порты и остальные переменные окружения. Создайте оба
подключаемых файла до запуска контейнера, чтобы вместо отсутствующих файлов
не были созданы каталоги.

Подготовьте конфигурацию сайта nginx из корня репозитория:

```sh
mkdir -p docker
cp conf/default.conf docker/nginx-site.conf
```

Внутри существующего блока `server` в `docker/nginx-site.conf` добавьте
директиву, разрешающую увеличенный размер загрузок PHP из примера:

```nginx
client_max_body_size 128m;
```

Файл сайта полностью заменяет стандартную конфигурацию сайта, поэтому должен
содержать её целиком. Лимит тела запроса nginx и `post_max_size` PHP должны
вмещать файл и служебные данные запроса: в примере для этого оставлен запас
сверх лимита файла в 120 МиБ. Чтобы заменить основной конфиг nginx, возьмите
за основу `conf/nginx.conf` и подключите свой файл в
`/var/www/html/conf/nginx.conf`. Путь для конфигурации сайта с SSL указан
в таблице выше.

При каждом запуске `start.sh` копирует эти файлы nginx, а затем применяет
переменные окружения: `WEBROOT` заменяет директивы `root` в `default*.conf`,
а `HIDE_NGINX_HEADERS` меняет `server_tokens` в основном конфиге. Подключайте
исходные файлы в `/var/www/html/conf/`, как в примере: подключение рабочих
файлов напрямую в `/etc/nginx/nginx.conf` или `/etc/nginx/conf.d/default.conf`
в режиме только для чтения помешает скрипту запуска обновить их.

Создайте `docker/php.ini` с дополнительными настройками PHP, например:

```ini
max_execution_time = 120
max_input_vars = 5000
opcache.memory_consumption = 256
```

Три переменные размеров `PHP_*` в примере Compose принимают целое число МиБ
без суффикса `M`. PHP читает дополнительные INI-файлы по алфавиту, поэтому
`zzz-custom.ini` загружается после настроек образа и создаваемого при запуске
`zz-runtime.ini`. Если директива задана и через переменную окружения, и в
`zzz-custom.ini`, приоритет имеет пользовательский файл. Не редактируйте
`zz-runtime.ini` напрямую: он пересоздаётся при каждом запуске. См.
[документацию по конфигурации PHP](https://www.php.net/manual/en/configuration.file.php).

Параметры пула PHP-FPM, например `pm.max_children`, задаются в отдельном
файле `.conf`, а не в `php.ini`. Например, создайте `docker/php-fpm.conf`:

```ini
[www]
pm.max_children = 32
pm.start_servers = 4
pm.min_spare_servers = 4
pm.max_spare_servers = 16
```

Добавьте ещё один элемент в `services.app.volumes` файла переопределений:

```yaml
- ./docker/php-fpm.conf:/usr/local/etc/php-fpm.d/zzzz-custom.conf:ro
```

Благодаря имени этот файл загружается после встроенного `zzz-app.conf`:
указанные настройки пула переопределяются, а пользователь рабочих процессов
и параметры сокета сохраняются.

Для параметров запуска Node.js используйте
[`NODE_OPTIONS`](https://nodejs.org/api/cli.html#node_optionsoptions)
с поддерживаемыми флагами. Пример ограничивает старое поколение памяти V8
значением 1024 МиБ; это не лимит памяти всего контейнера. Чтобы изменить
реестр npm, задайте `NPMMIRROR`. Node.js/npm входят в образ, но приложение
на Node.js автоматически не запускается. Постоянно работающее приложение
настройте отдельно, например через конфигурацию программы Supervisor
в `/etc/supervisor/conf.d/`.

После изменения Compose или подключённых файлов проверьте итоговую
конфигурацию и пересоздайте контейнер:

```sh
docker compose config --quiet
docker compose up -d --force-recreate app
docker compose logs app
```

Для варианта без Node.js уберите `NODE_OPTIONS` и явно указывайте оба файла
в каждой команде, например:

```sh
docker compose -f compose.without-node.yaml -f compose.override.yaml up -d --force-recreate app
```

Скрипт запуска проверяет конфигурацию nginx и PHP-FPM перед запуском их
процессов. Команда `docker compose exec app php --ini` показывает загруженные
INI-файлы PHP, а `docker compose exec app nginx -T` — конфигурацию nginx.

## Расширения PHP и производные образы

Помимо расширений, встроенных в официальный образ PHP, устанавливаются:

```text
amqp bcmath brotli exif gd gettext igbinary imagick imap intl ldap
memcached mongodb msgpack mysqli opcache pdo_mysql pdo_pgsql pgsql
redis soap sockets zip
```

Smoke-тест проверяет обязательные модули, поддержку JPEG/FreeType/WebP в GD,
кодирование PNG через Imagick, сжатие и распаковку Brotli, а также SQLite
через PDO. Дополнительно проверяются криптография Node.js, упаковка и установка
npm-пакетов без сети, выполнение npx, выполнение PHP по HTTP, статические
файлы, отсутствующие PHP-файлы, переопределение настроек, права каталогов
Laravel и перезапуск контейнера. Проверки подключённых каталогов контролируют
UID/GID рабочих процессов PHP, владельца и права новых файлов и каталогов,
доступ nginx, сохранение владельца файлов приложения и отклонение некорректных
настроек.
Также проверяются формирование тега с версиями и вывод отчёта при запуске
и после перезапуска. Команда `python3 tests/publish-check.py` проверяет теги
публикации и обработку ошибок без обращения к реестру.

Чтобы установить дополнительное расширение в свой образ:

```dockerfile
FROM ghcr.io/deadcxap/nginx-php8-fpm:latest
RUN install-php-extensions xdebug-stable
COPY . /var/www/html
ENV WEBROOT=/var/www/html/public
```

Установка зависимостей Composer/npm остаётся задачей вашего приложения.
Используйте отчёты о версиях и теги с версиями для проверки совместимости
приложения перед развёртыванием нового базового образа.
